# Lemo companion — motion timing, caption hold, camera moves, deterministic render, three.js post and orthographic depth of field, loudnorm mux, and font credits inside a lemo-opuscar film project, after the style is chosen

This skill is a companion, not a film director and not a renderer. The lemo-opuscar skill stays in charge of the style, the treatment, the story, voice, and music. Use this skill only when you are already inside a lemo-opuscar film project, the style is chosen, and the weak point is motion, caption timing, 3D picture, or asset preparation before mux. If the request is a film in general, a style choice, a treatment, or a film outside lemo-opuscar, do not use this skill; use lemo-opuscar instead, or say so. In particular, a request to choose a style or write a treatment is lemo-opuscar territory even if it mentions motion, captions, or cameras.

Priority: lemo-opuscar first for style, story, and delivery. This skill second, and only for the four areas above. Never let this skill override a style invariant in the chosen `STYLE.md`, never edit `core/` or `styles/` in the library, and never replace the lemo pipeline `window.render(t)` → still → ffmpeg mux with another pipeline.

Priority among this skill's own rules, when they conflict: subtitle hold (C1) outranks the news cut grid (B7) and outranks silent clipping (C4); the orthographic depth rule (D2) replaces, not merely outranks, the perspective post-module rule (D1) for orthographic scenes, and an orthographic scene is recorded as D2, not as D1; the silent-audio exception in E1 outranks the general rule that a mux warning is a defect; and the actual chosen `STYLE.md` outranks companion Aspiration rules and style-grammar rules, but does not override companion tool-contract rules (C4 export steps, D3 exact pins, E1 loudnorm targets, E4 output protection) by a mere mention: a conflict with a tool-contract rule must be reported as unresolvable within lemo tools, not resolved by noting it, and a style line only counts as an invariant if it states a rule for all films in that style, for example with always, must, or never, under a heading that states a style rule; a single demo choice, score detail, or example value is not an invariant, and if a line is ambiguous, treat it as not an invariant and let the companion rule apply. Further priorities: if the chosen STYLE.md preset list in C2 contains a fade, B3's default-fade defect does not apply to that listed fade, but a fade not in the preset list still fails; if the music grid BPM in A4 and the plan grid BPM in B7 differ, record both, let cuts follow B7 and accents follow A4; cuts are checked against the B7 grid and accents against the A4 grid, separately, and recording both BPMs with an explanation does not pass any alignment check between music and cuts — no such alignment is claimed when the grids differ; grain as a style effect follows E2's mux grain rule, not a STYLE.md mention alone, unless a style invariant explicitly states a grain value, in which case record it as a deviation from the default with a reason.

Labels on every rule say what the rule is, so you never present guidance as if a machine enforced it: [Enforced] means code or a tool forces it, [Aspiration] means guidance says it but no tool checks it, [Narrowed] means the original guidance was contradicted and the rule below is the narrowed, safe version, [Unverified model] means a borrowed model whose full source text was not retrieved and which has not been tested on lemo's pinned stack, [Prohibition] means a ban on teaching or using something, not a model to follow. Evidence, excluded rules, and the unverified list are in `references/PROVENANCE.md`. An explanation, reason, or plan acceptance never by itself passes a check: a deviation is recorded as a deviation, and delivery with a recorded deviation requires owner acceptance, except where a rule names an independent check that decides pass or fail (D2's rendered comparison is the model).

## How to work

1. Confirm you are in a lemo-opuscar film project with a style chosen and a project folder. If not, stop and use lemo-opuscar.
2. Name the weak area: motion, caption, 3D, or asset preparation. Work on that area only; do not drift into general directing.
3. Apply the rules in that section, in order, and keep every change inside the film's project folder.
4. Run the check given with each rule. A rule without a passing check is not done, except section F models, whose check is both that the code built with them still passes the checks in sections A-E and that the model's own mapping is checked: F3's transition window exists as a time window in `render(t)`, F5's windows all have an end, F6 shows no parent inheritance, and F2 uses at most five atomic rules per scene, otherwise report the excess; an F model is named as unverified wherever it is used, not presented as a checked rule.
5. Before delivery, run the short checklist at the end. Do not claim a film is ready from the guidance alone.

## A. Determinism and time

A1. [Narrowed] Make picture code deterministic inside `render(t)` only: no wall-clock time, no unseeded random, and no state carried from the previous frame, so any frame can be drawn alone, in any order. Reason: still rendering seeks arbitrary times, and a frame that depends on the previous frame or on the clock cannot be reproduced. Check: picture code is defined as code inside `render(t)` and functions it calls for picture, while orchestration code is the slot and render runner outside `render(t)`; if the boundary is unclear, treat the code as picture code. Check determinism by order-independence, not by grep alone: render the same time t twice with other times rendered between them, and confirm both frames are identical; a difference fails A1. Grep the picture code for `Date.now`, `performance.now`, `new Date`, `Math.random`, and `crypto` random calls as a verdict on comment-and-string-stripped code: a banned call in picture code fails A1 even if the order-independence test passes, because a banned call whose effect is cached on first render passes re-render comparison while still violating the prohibition; the only exception is a call inside a seeded helper (`mulberry`, `hash`). Mutation that re-derives scene state from t on every call — positions, rotations, opacity set from t — is not carried state and does not fail A1; carried state is a value read that a previous render call wrote (an accumulator, unseeded RNG state, a cache read from a previous frame without passing through t). A cache identifier binding under D6 is not itself a violation. Seeded helpers from `core/lib.js` (`mulberry`, `hash`) are used instead of unseeded random. Note: render orchestration code outside picture code does use wall-clock and random backoff for slots; that does not license random picture code, and an impasto-style fallback to unseeded random is a defect, not a default to copy. A build-time fallback is still a defect even when the seed is stored in the generated stroke: frames within one build stay consistent, but builds are not reproducible when the caller omits the seed, so two known demo engines that fall back this way (impasto at `impasto.js:333`, woodcut at `knife.js:20`) are examples of the defect, not precedents to copy.
A2. [Aspiration] Express motion as reusable functions of time from `core/lib.js` — segments, easing, monotone interpolation, multi-dimensional tracks, and envelopes — instead of hard-coding a value per frame. Reason: a function of time can be sought, reviewed, and reused; a per-frame literal cannot. Check: motion code imports and calls `core/lib.js` helpers, and a search for per-frame literals in the motion code finds no pose table replacing a time function. Note: the helpers exist in the library, but no tool forces their use, so this rule is guidance, not machine-enforced. Boundary with F1: a keyframe track is keys at named times interpolated by helpers into a function of t, while a pose table is a literal pose per frame or per time step with no interpolation function; if the code contains a per-frame literal table, it is a pose table, not a track, even if it is called a track. Further checks on the same helpers: every cue progress goes through `seg` or `clamp`, and a raw `lerp` with unclamped progress is a defect, because it overshoots the segment ends. Declare one rounding policy per film in the plan, for example coordinates to a fixed number of decimals and times to milliseconds, and treat mixed ad-hoc `round` or `toFixed` use as a defect, because no public precision is declared in the library. Do not judge scale motion by linear numbers alone: linear scale reads as decelerating as it grows, so check scale motion in still review rather than by its numbers; no compensation curve is prescribed here, because none was measured on lemo.
A3. [Aspiration] Keep one timeline of your own as the single source of truth for segments, tempo, beats, and accents, and export it as JSON so music, mix, subtitles, and checks read the same numbers. Reason: picture, sound, and captions drift apart when each stage keeps its own timings. Check: one planning timeline file exists in the project; the cue times in the SRT match the C5 driving timeline, not the planning timeline; and the mix notes match the timeline they describe, with that timeline named. If the planning and driving timelines differ, the SRT follows the driving timeline, the difference is recorded, and the difference is not a failure; the C5 source rule outranks this match check on divergence. Warning: lemo core does not read this timeline; it is your own discipline, not a lemo-enforced format, and only a minority of library styles ship a timeline file, so do not expect any lemo tool to consume it. Three timelines are distinct and must not be merged by label: this A3 planning timeline, the C5 driving timeline that the subtitle renderer actually reads, and caption JSON with timestamp fields, which F8 bans. Do not use the A3 planning timeline as the subtitle export source; generate subtitles from the C5 driving timeline, and if the same file serves both roles, record that it is the driving timeline, not merely planning data, and that its cue times are the ones checked in C1, using t0 and t1 in seconds like `srt.py`, not timestamp fields.
A4. [Aspiration] Map cues to the music grid before animating, and aim for picture accents on the same grid with near-zero offset. Reason: music that chases picture after the fact never locks. Check: a cue map exists before animation starts, and a cue check reports the maximum deviation in milliseconds; there is no pass threshold in the library, so report the measured deviation, and record any deviation of one frame or more (41.7 ms at 24 fps) in the cue map. An explanation in the plan does not pass a deviation: a deviation of one frame or more fails the grid-alignment check; the film may still be delivered with the deviation recorded as a known deviation accepted by the owner, but it must not be reported as aligned. A4's music grid is not B7's plan grid: if their BPMs differ, follow the priority section, do not use cue times as cut times unless the plan explicitly maps them. An offset change voids prior alignment evidence: after any start-offset change, re-run the alignment check (visual hits against music by cuecheck; voice alignment by listening, since no tool checks it) instead of reusing the earlier result.
A5. [Narrowed] Read the chosen style's actual `STYLE.md` before applying any rule below, and do not assume its invariants are clean. Reason: the template says a style file holds only invariants, but in practice score details such as BPM appear in several real style files, and nine of 59 style files differ in heading structure, so an assumed invariant can be wrong for the chosen style. Check: the chosen style file was read in full for this film, and any rule that conflicts with it is resolved under the priority section, not by merely noting the conflict: style invariants outrank companion Aspiration and style-grammar rules, while a conflict with a companion tool-contract rule must be reported as unresolvable within lemo tools. This rule does not make this skill a style-maintenance skill; it only stops the companion from trusting an assumed style file.
A6. [Aspiration] Declare a film-local named preset list for easings and springs once, and reuse it across scenes, with a different ease per segment where the track needs one. Reason: named presets keep motion consistent and reviewable, while ad-hoc numeric constants per scene drift silently. Check: the plan or film code lists each preset by name with its parameters, every scene refers to a preset by name, and a search for bare easing numbers outside the preset list finds none. The library's `core/lib.js` provides named functions but no preset list, so the list is the film's own; do not import a foreign preset set.
A7. [Aspiration] Validate load-time parameters once, at load, and fail before the first still if one is missing. Reason: a parameter read mid-render fails a render that is already underway, while a load-time failure is cheap and visible. Check: the page checks every load-time parameter it needs (for example query parameters) before setting READY; the plan lists which parameters are required and which have defaults. A run with a REQUIRED parameter removed fails before any still is produced, never halfway through rendering; a run with a DEFAULTED parameter removed must not fail, because the default applies — a check that fails on a removed defaulted parameter is a wrong check, not a failed film.

## B. Motion and camera

B1. [Aspiration] Give every meaningful motion in smooth motion preparation, action, and settle; change pose by keyframe and easing, never by a sudden pose jump, except one intentional one-frame comic pop named in the plan. Reason: a jump without preparation reads as a glitch, not as motion. Check: step the action at 0.2 s intervals, enlarged, using still rendering with a range step, and confirm each pose change has a preparation and a settle frame; for the comic pop, render the pop frame itself at full size together with the frames before and after it, and confirm the pop is intentional and readable, because naming a pop is a label, not a visual test. Stepped styles are not covered by this rule; they follow B2 instead, and the comic pop is a single named frame, not a stepped sequence.
B2. [Aspiration] For any stepped style, including stop-motion, pixel, and cel looks, step only the character at the low rate while camera and light stay smooth every frame. Reason: a stepped camera reads as lag, while a stepped character reads as the style. Check: in the stepped scene, camera and light values change every frame, and only character values step, and each step is readable with no intermediate blur. Stepped styles beyond the three named examples fall under this rule, not between B1 and B2.
B3. [Aspiration] Use at least four different camera moves, one memorable signature shot, and transitions built from the style's own material instead of a default fade. Reason: one camera grammar repeated for a whole film flattens it, and a default fade breaks the medium. Check: list each camera move with its type, duration, and start and end frame, and name the signature shot, which is one shot that is specific to the scene and memorable, not merely one more move; a default fade with no material reason is a defect. Exception: a locked-off style, named as such in its STYLE.md, is exempt from the four-move count, and the exemption must be noted, not silently assumed.
B4. [Aspiration] Change tempo clearly, give the audience one breathing beat, and go faster with fewer words on screen, not by cutting before the viewer has finished reading. Reason: a film at one even speed has failed, and a cut that interrupts reading loses the information. Check: the tempo change is implemented in the scene code, not only named in the tempo plan: cut times and pacing follow the named acceleration or deceleration, and the breathing beat exists in the rendered timeline as a pause of at least 1 s with no new information after a dense passage; a plan that names a tempo change the code does not implement does not pass; every cut respects the subtitle hold in C1, which is the cut rule here, and B4 does not invent a second cut rule, and cue times from A4 are not cut times unless the plan explicitly maps them to cuts.
B5. [Aspiration] Review the main action at 0.2 s intervals at enlarged size, and check expression at final projection size, especially eyebrow direction. Reason: a small detail such as eyebrow direction changes emotional meaning, and it is invisible at thumbnail size. Check: short events are enumerated from the plan before review, as a list of pops, flashes, and blinks with their times, not discovered by the 0.2 s review alone; a contact sheet or a still range at 0.2 s steps exists, the expression check was done at final size, not only at thumbnail size, and each listed short event was also checked at full frame rate around that event, because a 0.2 s review alone misses one-frame events.
B6. [Aspiration] Keep the subject large enough, near enough to centre, and contrasted enough to read. Reason: a subject that is too small, too far, edge-clipped, too dark, or coloured like its background is listed as a failure. Check: in the rendered frames, the subject is not clipped at the edge and is not lost against the background, and the check reports the subject's bounding-box share of the frame and its lightness difference from the background; no pass threshold for those numbers exists in the library, so report them, and reporting alone does not pass a clipped or dark subject, which is a defect regardless of the numbers.
B7. [Aspiration, news styles only] Cut and transition on a fixed grid, not freely by feeling. Reason: news styles read as news because their cuts sit on the grid. Check: the scene plan states the BPM, whether the grid is beat or half-beat, and the grid origin (the time of the grid's zero: the music start / first downbeat time), and every cut time satisfies (cut minus origin) is a multiple of the grid step to millisecond rounding; when the music starts after picture start or its first beat is offset, the plan must declare that offset as the origin — an undeclared offset makes t=0-aligned cuts fail the grid check, not pass, where beat step in seconds is 60 divided by BPM and half-beat step is 30 divided by BPM, so at 120 BPM a beat is 0.5 s and a half-beat is 0.25 s, not 0.5 s. If a grid cut would break the subtitle hold in C1, C1 wins and the cut moves, and that moved cut is recorded as a C1 exception, not counted as a grid failure.
B8. [Aspiration] Declare each scene's subframe policy in the plan: smooth or stepped, with the step size when stepped; the default is smooth. Reason: smooth and stepped behaviour both exist in lemo, but an undeclared policy lets a scene drift between them. Check: the plan names the policy for every scene, and the rendered frames match it: smooth scenes change every frame, stepped scenes step only at the declared rate.
B9. [Aspiration] Declare each scene's fit and anchor before drawing: contain or cover, and the anchor point, with no default stretch. Reason: without a declared fit, content is stretched or cropped by accident. Check: fit and anchor appear in the scene code as values actually used for fitting, not as plan-only statements: a plan that states fit and anchor while the scene code contains no fit computation using them does not pass; and when text width is measured for fitting, the width is rounded up, because rounding down shrinks the fit below the text.
B10. [Aspiration] Write stagger as per-element window offsets with a named origin: first, centre, or edge. Reason: a stagger without a named origin cannot be reviewed or shifted as a whole. Check: the origin is a code binding, not a plan-only name: the origin appears in the scene code as a declared binding and at every use site, with the per-element offset for every staggered group; a name that appears only in the plan, in prose, in a comment, or in a string table is not a stagger origin, and shifting the origin binding in code shifts the whole group.

## C. Caption and readability

C1. [Aspiration] Hold every subtitle at least 1.8 s, and never shorter than the spoken line plus 0.6 s, with hold time proportional to length. Reason: a subtitle that leaves before it can be read loses the line. Check in two stages, because the exporter cannot fix a bad cue list: first check the cue list before export, then check the exported `.srt` after export, and reject the export if the second check fails. In both stages, parse the cues, compute end minus start for every cue, and fail any cue below 1.8 s or below its spoken duration plus 0.6 s, where spoken duration is the duration of the spoken audio for that cue from the audio events or timeline, or, if no audio exists yet, the planned speech duration recorded in the timeline, with its source named. Warning: the library's readcheck tool checks on-screen text by a different formula and does not check the subtitle bar, so do not claim readcheck passing proves this rule. Priority: if the next cue starts before the required hold ends, fix the cue list, not the exporter: re-time the next cue later, or merge the cues; shortening the earlier cue's text alone is not a fix, because it does not shorten spoken audio, and it is available only if the spoken audio is re-recorded or re-synthesised to the shortened text and the spoken duration is re-measured, never by re-estimating planned speech from shortened text. If none of re-time, merge, or re-recorded shortening is possible, the cue list does not pass C1: record the conflict, list the violating cues, and deliver only as a recorded C1 exception accepted by the owner, or block delivery and return the film to the voice stage for re-recording. When an exception is accepted, prefer the least harm in this order: a short hold (the line shows briefly) over a moved cue (the line shows at the wrong time) over merged cues from distinct speakers (the line attributes speech to the wrong speaker), because misattribution states something false while timing errors only degrade timing; the chosen harm and its reason are recorded with the exception. This priority also resolves the C1 versus B7 grid conflict in favour of C1.
C2. [Aspiration] One screen carries one main idea, transitions stay inside a preset set, and for charts a transition must be a chart operation, not a fade effect. Reason: two ideas on one screen compete, and a fade over a chart hides the data change. Check: each screen in the plan names its single idea, the preset set is the set of transitions listed in the chosen STYLE.md, not a global list, and each chart transition names the chart operation it performs, such as bar growth, line draw, or value change. Priority within this rule: for chart transitions, the chart-operation requirement governs over preset-set membership — a fade is never a chart operation, even if the preset list contains a fade, and a chart transition that is a fade fails even when listed; for non-chart transitions, preset-set membership governs. When the preset list contains only a fade, the preset-set check does not pass or fail chart transitions (it is not applicable to them); the chart-operation check decides them.
C3. [Aspiration] Treat a subtitle covering the subject and an empty frame inside a transition as defects at delivery, not as style choices. Reason: both hide the film instead of serving it. Check: in the rendered frames, no subtitle box covers the main action, and no transition contains an empty frame; no tool detects subject coverage automatically, so the check is visual, and the check reports the subtitle box position and the subject position, and reporting those positions alone does not pass a subtitle that covers the subject.
C4. [Enforced] Export subtitles from a cue list with start and end times: sort by start, clip a cue at the next cue's start on overlap, and round to milliseconds before splitting hours, minutes, and seconds. Reason: unsorted or overlapping cues produce a broken or mis-timed subtitle file, and rounding after splitting loses a millisecond at the boundary. Check: the exported `.srt` is sorted, no two cues overlap, and the exporter used is the lemo subtitle exporter (`core/render/srt.py`) or an equivalent that performs the same three steps; do not hand-write the file, and do not claim an exporter is equivalent without testing it on a sample with an overlap, a rounding boundary, and a sort-order case, and comparing its output with `srt.py` for identical cue start and end times to the millisecond and identical text for every cue in the sample; one sample establishes equivalence only for the tested cases, and equivalence must be re-tested if the exporter changes. Clipping is what `srt.py` does, and it cannot re-time, merge, or refuse: if clipping breaks C1, the exported file fails C1 and must be rejected, and the fix is in the cue list under C1, not in the exporter. Rounding is to whole milliseconds before splitting; there is no separate timestampMs field in this rule. The exporter clips silently, so the agent running an export must list every cue it clipped, with a reviewable reason for each; a clipped cue with no reason is an unreviewed change to the cue list, and if clipping breaks C1 the export fails C1 as above.
C5. [Aspiration, with a caveat] Keep audio events and subtitles separate: the event file carries only durations and audio events, while the subtitle file must come from the timeline that actually drives on-screen subtitles, so the two layers match. Reason: mixing them makes the subtitle file drift from what is on screen. Check: the event export and the subtitle export are different files from different sources, and the subtitle cues match the on-screen subtitle timeline, where the driving timeline is defined as the file the subtitle renderer actually reads, not any planning file. Caveat: no code verifies that the cues file really equals the on-screen timeline, so this rule is guidance with a manual provenance check, not machine-enforced, and the provenance of the cues file must be confirmed by hand; if the A3 planning timeline is the file the renderer reads, then it is the driving timeline for this purpose, and its cue times are the ones checked in C1.
C6. [Aspiration] Preserve whitespace when film code joins caption words for display: joining words without their whitespace glues them together. Reason: the exporter writes cue text verbatim, but display-side joining is per-style film code and no tool checks it. Check: in still review, joined caption text reads with its word spaces intact; readcheck compares full on-screen text, not word joins, so it does not cover this check.

## D. 3D and picture

D1. [Enforced, perspective scenes only] Keep the 3D post chain in this order: physical depth of field with GTAO, then bloom, then grade and vignette, then tone mapping, using the lemo post module (`core/three/post.js`) and its internal supersampling setting. Reason: reordering the chain changes the picture in ways that are hard to debug, and the module's order is the verified order. Check: the scene's post setup calls the module in that order, and any caller that sets supersampling or ambient occlusion states its values explicitly. D1 is a perspective-scene rule: an orthographic scene does not satisfy D1, and must not be reported as satisfying D1.
D2. [Narrowed] Before using depth of field, check the camera type: the core depth code uses a perspective-camera conversion, so an orthographic camera without changing that conversion silently breaks depth of field. Reason: a silent break looks like a rendering bug somewhere else. Check: if the scene uses an orthographic camera, do not use core depth of field unchanged; use a scene-local post copy with an orthographic depth conversion, keeping the same chain order as D1, and never edit `core/three/post.js` to fix it. Record the scene as D2, not D1, and test the conversion, not merely list it: for a scene with distinct near and far content, render a still with depth of field on and off at the same time, and confirm the depth version shows depth-dependent blur, with near and far blur differing; for a scene whose content lies on effectively one depth plane, where near/far differentiation cannot appear, use the focus-sweep test instead: render at two different focus distances and confirm the blur changes accordingly; if neither test shows the expected change, D2 fails. If the local copy drops GTAO or supersampling, that is a recorded deviation from D1's chain, with a reason in the scene plan, and listing it alone does not make it pass; the rendered comparison above is the check. Focus is a world distance. For orthographic scenes, target-versus-distance behaviour under the orthographic conversion is [chưa kiểm chứng]: do not transfer perspective focus numbers to an orthographic scene unmeasured, and do not rely on any target-overrides-distance rule on orthographic scenes; set focus by distance and record the distance used.
D3. [Enforced] Pin the verified render stack by machine: Node 20 or newer as a minimum, three 0.170 exactly, and playwright-core 1.63 exactly, as pinned in the library lockfile. Reason: 3D animation examples written for a newer three version may not run on the pinned version, and an unpinned stack makes a film unreproducible. Check: `node --version` is 20 or newer, and either the project's lockfile or the library lockfile pins three 0.170 and playwright-core 1.63 exactly; a lockfile pinning different numbers does not pass, and do not upgrade three to chase an example without a render test. Note on the limit of this check: reading a lockfile proves the pin, not the installed version, so if the project has installed packages, also check the installed three version and report a mismatch as a defect; if no packages are installed, record that the installed version was not verified, and do not claim the lockfile read alone proves the installed stack. Process gate on top of the pin: any change to the three version in the lockfile must be accompanied by still review of every style that uses post-processing or depth-of-field helpers; a pin change without that review is a defect, because helpers written for one three version may not behave the same on another.
D4. [Aspiration] Set group opacity by setting every material's opacity inside the same `render(t)` call, never by assuming a group opacity. Reason: a three `Group` has no opacity of its own, so a group-opacity assignment silently does nothing. Check: a search for opacity assignments on groups finds none, and every material that should fade has its opacity set in `render(t)`.
D5. [Aspiration] Declare the evaluation order inside one frame in the plan, for example camera, then animation, then post-processing, and keep the code in that order. Reason: order inside a frame decides what post-processing sees, and an undeclared order drifts when scenes are edited. Check: the plan states the order, and the scene code follows it. This is order inside one frame, not the directing evaluation order excluded in PROVENANCE.
D6. [Aspiration] Share geometry and material through caches, in the style of the brick and paper-popup caches, instead of creating new ones per mesh in a loop. Reason: per-mesh creation in a loop wastes memory and render time, and the failure is silent. A cache is a code binding, not a label: declare each shared geometry or material under an identifier in the scene code, and reference that identifier at every use site; a name that appears only in the plan, in prose, in a comment, or in a string table is not a cache, and a declared binding that is never referenced is dead code, not sharing. Check: scene code that builds many meshes reuses cached geometry and material, a loop that creates new geometry or material per mesh is a defect, and every cache identifier named in the plan appears in the scene code as a declared binding and at a use site.
D7. [Aspiration] After writing instance matrices on an InstancedMesh, set `instanceMatrix.needsUpdate`. Reason: without the flag, the renderer keeps the previous matrices and the instances do not move. Check: every write to instance matrices in the scene is followed by the flag before the next render.
D8. [Aspiration] Use one camera per post-processing composer. Reason: a composer built around one camera and one scene gives a predictable picture; mixing cameras inside one composer does not. Check: each composer in the scene has exactly one camera. Sanctioned exception, declared per shot: the hd-2d pattern reassigns the pass scene per shot while sharing one camera; the reassignment must be declared in the shot plan, not done silently.
D9. [Aspiration] Give transparent objects an explicit `renderOrder`. Reason: transparent objects are sorted back-to-front, and without an explicit order, overlapping transparencies sort by accident. Check: every transparent object in the scene sets `renderOrder`, and still review shows no transparency sorting artefacts.
## E. Asset, audio, and mux

E1. [Enforced] Master with two-pass loudnorm to -14 LUFS, true peak -1.2 dB, and LRA 11, then re-measure and warn on deviation, using the lemo mux script (`core/render/mux.sh`). Reason: single-pass normalisation misses the target by about half a loudness unit, and an unmeasured mix can clip. Check: run mux, read its measured loudness, LRA, and true peak, and confirm loudness is within 1 LU of -14 and true peak is at or below -1.2 dB, the loudnorm target; the script's own warning threshold (-1 dB) is reported alongside but does not pass a peak above the target: a peak above -1.2 dB fails the check, not a note to ignore. LRA has no separate pass threshold in the script, so report the measured LRA against the target 11. An explanation of an LRA deviation does not pass the loudnorm check: the check passes on loudness within 1 LU of -14 and true peak at or below -1.2 dB; an LRA deviation is a recorded deviation, and delivery with it requires owner acceptance of the recorded deviation. A warning from mux is a defect to fix, not a note to ignore, except the silent-audio skip warning, which is the script's documented exception, defined operationally as: the first-pass loudnorm measurement returns inf or nan for loudness, peak, LRA, threshold, or offset, or the measured loudness is below -70 LUFS, with no decoder errors, exactly as `mux.sh` implements it. That definition alone does not prove a voice track exists: separately confirm the audio stream exists, its duration matches picture within the mux pad and trim rules, and, if the timeline contains voice cues, that voice audio is present in the mix — measured, not asserted: for each voice-cue window, run ffmpeg volumedetect on the mix and confirm mean_volume is above -20 dBFS; peak volume alone does not prove voice presence, because a loud music bed reaches the same peaks. If voice cues exist but the mix is silent, that is a defect, not a silent exception, and must not be recorded as confirmed truly silent. If the same film's bed-only windows measure above -24 dBFS mean_volume, report both the voice-window and bed-only numbers and do not claim voice presence from the absolute floor alone. Measurement transport: the mux script reads its first-pass loudnorm values from JSON scraped out of the combined ffmpeg output stream, not from a separate measurement file, so if that JSON block is missing or unparseable, the measurement has failed and no scraped or partial value counts as measured. Linear-mode limit: the script applies linear second-pass gain on any finite measurement set, without checking that measured LRA is at or below the target 11 or that post-gain true peak stays within bounds, and its fallback is to skip normalisation, never a dynamic mode — so the post-mux re-measure above is the only guard, and its warning is a defect to fix, not a note. Guard on the invocation itself: never drop the explicit loudnorm arguments from a mux call, because without them the tool falls back to its own defaults (-24 LUFS, true peak -2 dB, LRA 7), which differ from lemo's -14 LUFS, -1.2 dB, and LRA 11 targets and would silently re-target the film.
E2. [Enforced] Add film grain at mux with ffmpeg, not by drawing grain in the page, and use zero grain for pixel and vector styles, and the script default grain 2 for other styles. Reason: in-page grain hurts compression and render speed, while mux grain is cheap and uniform. Check: the mux call passes the grain argument, it is zero for pixel and vector styles, and it is 2, or the style's explicitly stated grain value, for other styles; a reason recorded for a non-default grain value explains the value but does not pass the check — the check is the grain argument in the mux call itself; passing zero for every style does not pass. No page code draws generic film grain; intentional CRT or tape noise as a style effect is a different effect and must be named in the scene plan as a style effect, and naming it does not exempt the mux grain argument, which stays zero for pixel and vector styles.
E3. [Aspiration] Use only CC0, CC BY, or OFL material, list each item with source and licence in CREDITS, self-host OFL fonts in the project, never link external fonts at render time, and subset CJK fonts to exactly the characters used. Reason: an unlisted or externally linked asset can break the film or its licence at render time. Check: a CREDITS file exists and lists every non-code asset with source and licence, the project fonts are self-hosted, a search for external font links across the project returns nothing, including `fonts.googleapis`, `@import` of a font URL, `<link>` tags to external fonts, `@font-face` src URLs, script-injected font links, and any http or https font URL from a non-self-hosted CDN, and CJK subsets cover exactly a DECLARED character set, where exactly means the subset character set equals the declared set, with no missing and no extras, verified with `python3 -m fontTools.subset`, not by assertion. The declared set is fixed before render and has three parts: (a) the SRT text, (b) literal on-screen strings declared in the plan, (c) generated-text classes declared in the plan before render, each with its character set (for example counter digits 0-9, date separators). Canvas and WebGL text exists only as pixels after render, so text generated at render time cannot be enumerated beforehand: only declared classes are subsetted, and any rendered text outside the declared set is a recorded deviation, not a pass — still review must catch rendered text outside the declared set. Text strings in project code that are never displayed (file paths, keys, URLs, error messages, format strings) are not part of the displayed set and must not be counted. Also declare the font fallback order explicitly in the film code or plan, and do not rely on the browser's default order: an undeclared fallback changes the face silently when the first choice is missing.
E4. [Enforced] Protect mux output: a failed ffmpeg step leaves no partial file, truly silent audio skips normalisation with a warning, short audio is padded with silence to picture end, and long audio is trimmed to picture. Reason: a partial or mismatched file looks finished until it is played. Check: after mux, the output exists, is non-empty, and its duration matches picture within the mux pad threshold of 0.02 s; and the failure path was tested, not only the success path, by running a mux with a deliberately missing input in a temp directory and confirming no partial output file remains. Note on the limit of that test: it proves no partial file on an early failure, not on a mid-encode failure; the mid-encode protection is `mux.sh`'s own behaviour of removing the output on ffmpeg failure, which is code, not a test result, and must be cited as such, not claimed as tested. Further output-protection checks, all agent-side because the script does not enforce them: a skipped pad is a failure, not a success, because the script silently skips padding when an audio or video duration is not greater than zero and there is no unknown-duration sentinel; never re-run mux onto a delivered file without renaming it or backing it up first, because the script overwrites with `-y` and a re-run silently replaces a finished file instead of erroring; after any mux run interrupted or killed mid-encode, re-verify the output from scratch (duration and loudness) and never present an interrupted run's output as finished, since the script sets no signal trap and a killed long mux can leave a truncated file; and after mux, verify faststart (moov at the front) and seekability, which the script chooses but never checks itself.
E5. [Enforced, prerequisite only] Use the lemo render contract to test motion: the page exposes duration and a `render(t)` function, and still rendering seeks any time and outputs a JPEG. Reason: without this contract, motion cannot be reviewed frame by frame. Check: still rendering at two different times both succeed and each matches the expected scene state at that time; for a scene with motion, the two stills must differ in the expected way stated in the plan, such as an object position change, and for a scene that is static by design, identical JPEGs are correct and are not a failure, because the check is that seeking works and the state matches, not merely that two JPEGs were produced. Do not expand this rule into a full pipeline tutorial; the full pipeline belongs to lemo-opuscar. Two further prerequisite checks: the duration must be finite before rendering, because the positivity checks in the render tools pass `Infinity` and a non-finite duration then corrupts the frame count; and READY is a delegated gate, not a tool guarantee — verify the page loads its fonts before setting READY. A missing required asset is a defect, not the tool's optional-file warning: the plan lists which assets are required, and the check compares fetch results against that list — a 404 on a listed-required asset is a defect, a 404 on an unlisted asset is not judged by this rule. A page that sets READY early is a defect only when early-READY is shown by a named signal: the page's font-load completion signal compared against the READY time; without such a signal, record that READY-early could not be checked, and do not claim it was checked.
E6. [Aspiration] Record the delivered render's settings in the plan — fps, resolution, and frame range — and verify the delivered file matches them. Reason: settings given only as command arguments leave no record, so a re-render at different settings can be mistaken for the same film. Check: the plan states the settings, and the delivered file's fps, size, and duration match them. Known exception to flag, not a general rule: the whiteboard motion-blur step assumes 24 fps (`dt = 1 / 24`), so a render at any other fps must flag that step for review.
E7. [Aspiration] Before mux, confirm the required encoders are present, and on a mux audio failure, name the codec. Reason: the mux script only reports a missing audio stream and only checks the stream type, so a missing encoder or an unsupported codec is reported late and vaguely. Check: an encoder listing shows libx264 and AAC available before mux, and if mux fails for audio, a probe names the actual codec instead of only reporting no audio stream.
E8. [Aspiration] Do not assume the mux colour default is sRGB: the default is yuvj420p with bt470bg, and bt709 is opt-in through `LEMO_COLOR`. Reason: a film graded assuming sRGB or bt709 but muxed at the default is colour-shifted without any warning, and no sRGB clamp exists in the pipeline. Check: if the film assumes sRGB or bt709, the mux call sets `LEMO_COLOR` explicitly and the delivered file's colour metadata is verified; otherwise the default is recorded as accepted.

## F. Borrowed models — unverified, use with care

Every model in this section is [Unverified model]: its full source skill text was not retrieved, only a short public summary, and it has not been tested on lemo's pinned three 0.170. Use a model only as a way to structure your own code inside `render(t)`; never install its runtime, never copy its foreign contract into lemo, and never present it as a lemo rule. If a model below conflicts with a rule in sections A-E, sections A-E win.

F1. [Unverified model] Structure 3D motion as keyframe tracks evaluated at time t, using the lemo time-function helpers, instead of hand-tweening every frame. Mapping: a keyframe track is a function of t inside `render(t)`, and still rendering captures it at any t. Not included: named clip objects, clip graphs, or playback controls, which lemo does not have.
F2. [Unverified model] Compose motion from a few atomic rules per scene, not by lifting a whole blueprint. Mapping: each scene uses a few pure functions of t inside `render(t)`; there is no rule registry or blueprint file in lemo, and composition stays hand-written per film.
F3. [Unverified model] Treat a scene as phases bound to subtitle cue windows, and treat the transition between scenes as its own step inside `render(t)`. Mapping: phases are time windows in the scene plan, and the transition is a time window in `render(t)`, not a separate transition object; mux only joins frames and does not perform the transition.
F4. [Unverified model] Animate position, scale, rotation, and opacity of Three.js objects inside `render(t)`, not DOM layout properties. Mapping: lemo renders on canvas and WebGL, so DOM layout concepts do not apply directly; there is no auto-opacity alias in lemo, and opacity is handled through the scene's own alpha handling.
F5. [Unverified model] Order motion with relative time offsets, readable labels, and nested structure, all evaluated at time t, with every window finite. Mapping: a label is a cue or phase name whose time is written in the scene plan, and still rendering seeks by seconds, not by label; there is no label-seek API in lemo, and no timeline repeat mechanism, so do not assume one.
F6. [Unverified model] Set per-scene default duration and ease in the scene's own configuration. Mapping: defaults live in the scene function, not in an inherited timeline defaults object, which lemo does not have; a child does not inherit duration or ease from a parent automatically, and an explicit value at a use site overrides the scene default, while an omitted value falls back to the scene default, not to a parent default.
F7. [Unverified model] Group caption words into display chunks by cue or clause, not by a token time window. Mapping: lemo captions chunk by cue and clause, and word timings are used to time a pen or a reveal, not to build display pages; there is no display-page window value in lemo, and no caption page-break flag.
F8. [Prohibition] Do not teach skeletal animation, morph targets, clip blending by weight, label seeking, caption JSON with millisecond timestamp fields, or a caption page-break flag from this skill. Reason: none of those is implemented in lemo, their examples target a newer three version, and their full source text was not retrieved. If a film genuinely needs one of them, stop and ask for a separate, tested decision; do not improvise it from a summary. Note: this ban is on caption JSON with timestamp fields and on a page-break flag; it does not ban the agent-owned planning timeline JSON in A3, nor the millisecond rounding in C4, which is a rounding step, not a timestamp field, and it does not ban the C5 driving timeline, which uses t0 and t1 in seconds like `srt.py`; if a planning timeline becomes the file the subtitle renderer reads, it is the driving timeline under C5, not merely planning data.

## Do not do

The items below are prohibitions from this skill, not machine-enforced claims, and they carry no [Enforced] label for that reason.

- Do not install, import, or copy a Remotion, GSAP, HyperFrames, or other render runtime into a lemo project, and do not replace still rendering or mux with one.
- Do not use scroll-driven timelines, React timelines, Remotion Studio caption rendering, WebGPU rendering, or a newer three version without a render test on the pinned stack.
- Do not use Vietnamese voice prosody rules from this skill; this skill contains none, because no approved source supported them.
- Do not copy text verbatim from the lemo library or from a surveyed skill into a film or into another skill; paraphrase, and keep evidence in `references/PROVENANCE.md`.
- Do not use CSS keyframe or CSS animation for film motion: still rendering captures the page at wall-clock time, not at `t`, so CSS-timed motion is uncontrolled, not forbidden by code — check by grep, which currently finds no such animation in library code.
- Do not pause or resume rendering on page visibility to save GPU: a visibility-driven pause breaks determinism, because rendering must depend only on `t`.
- Do not present an [Aspiration] or [Unverified model] rule as if a tool enforced it, and do not present a narrowed rule without its narrowing.
